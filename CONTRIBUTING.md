# Contributing to Pasto

Thanks for wanting to help. Pasto is a small project maintained in spare time, so a little preparation goes a long
way: it makes your change easier to review and more likely to land.

By taking part you agree to follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Before you start

- **Bugs.** Search the [issues](https://github.com/jnjambrin0/Pasto/issues) first, then open one with the bug report
  form. Never paste real clipboard contents or personal data; describe them instead.
- **Security problems** go through a private report, never a public issue: see [SECURITY.md](SECURITY.md).
- **Features and larger changes.** Open an issue (feature request form) and agree on the approach before writing
  code. A new module, a new dependency, a new permission or anything that sends data off the Mac needs that
  discussion first; small fixes and polish can go straight to a pull request.

## Setting up

Read [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md): requirements (macOS 27, Xcode 27.2), how to sign development
builds with your own team, the scripts, the debug launch arguments and the conventions. [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)
explains how the modules fit together.

```bash
scripts/test.sh                    # unit tests
scripts/build.sh                   # Debug build
scripts/run.sh --in-memory-store   # launch without touching a real history
```

## Making a change

1. Fork the repository and create a branch from `main`, named for what it does: `fix/search-crash-on-emoji`,
   `feature/pinboard-shortcuts`, `docs/architecture-typo`.
2. Keep each pull request to one change. Refactors go in their own pull request, separate from behaviour changes.
3. Follow the module, concurrency and style rules in [DEVELOPMENT.md](docs/DEVELOPMENT.md). In particular:
   dependencies only point down the layers, feature modules never import each other, the main actor owns the UI,
   one background writer owns the store, and nothing copied ever reaches the logs.
4. Add or update unit tests for any logic you change (pure logic only; there are no UI test suites). Check visible
   changes by hand in light and dark mode, in English and Spanish, and with VoiceOver for anything interactive.
5. Run `scripts/build.sh` (no new warnings) and `scripts/test.sh` (all green) before pushing.

### Commits

- Write commit messages in English, in the imperative, with a short summary line (about 70 characters at most)
  that says what changes for the user or the code: `Keep the selection when a search is cleared`.
- Add a body when the *why* is not obvious from the diff: what was wrong, and why this is the right fix.
- Keep commits focused; squash fix-up commits before asking for review.

### Localisation

Pasto ships in **English and Spanish**, and every user-facing string must exist in both.

- Put new strings in the module's string catalog (`Resources/Localizable.xcstrings`) through its strings type, with
  a semantic key and the English text as the fallback (see [Localisation](docs/DEVELOPMENT.md#localisation)).
- Fill in the Spanish value and mark both as translated. `StringCatalogTests` fails if a key is missing a language,
  is empty or stale, or has different placeholders in each language.
- If you do not speak Spanish, say so in the pull request and leave your best attempt; it will be reviewed.

### Code and assets must be yours

Contribute only work you wrote yourself or that is available under a licence compatible with MIT, and say where
anything third-party comes from. Do **not** submit code, images, icons, sounds, text or other assets taken from
other products, even as placeholders. Pasto's design is its own; images and sounds are generated by the tools in
`Tools/` or come from `Design/`.

## Pull requests

Open the pull request against `main` and fill in the template: what changes and why, how you checked it,
screenshots for visible changes, and the linked issue. CI builds the package and runs the tests. Expect review
comments; they are about the code, never about you. Once approved, the maintainer merges it.
